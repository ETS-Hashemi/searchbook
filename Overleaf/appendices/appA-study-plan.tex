\chapter{The Twelve-Week Study Plan}
\label{ch:appA}
\index{study plan|(}

This appendix is the book's answer to a practical question: \emph{in which order, and at
what pace, should I work through these chapters if I want a working hybrid swarm planner in
three months?} It reproduces the twelve-week training plan that the book was built from,
maps every week to the chapters that teach it, and adds study notes, a capstone
description, a completion checklist and a traceability table. Read it once before you start
\cref{ch:ch01}, and return to it at the beginning of every week.

% ---------------------------------------------------------------------
\section{How to use this plan}
\label{sec:appA-intro}

\paragraph{Goal.}
The goal of the plan is to build enough theory and implementation skill to design a
\textbf{hybrid swarm planner}\index{hybrid architecture!capstone} that handles two very
different kinds of trouble: \emph{planned} conflicts between the drones you control, and
\emph{unexpected} moving obstacles such as an unknown drone crossing your formation. The
target outcome after twelve weeks is a working research prototype that combines a global
multi-agent path finding (MAPF) solver (conflict-based search, \cbs, or its
bounded-suboptimal variant \ecbs, \cref{ch:ch09,ch:ch10}), a reactive avoidance layer
(optimal reciprocal collision avoidance, \orca, or the dynamic window approach, DWA,
\cref{ch:ch13,ch:ch14}), a prediction layer (a Kalman filter or a long short-term memory
network, LSTM, \cref{ch:ch18,ch:ch20}) and a replanning layer (\dstarlite or \astar,
\cref{ch:ch04,ch:ch05}). \Cref{ch:ch24} describes how these pieces fit together and
\cref{ch:ch25} how to evaluate the result.

\begin{keyidea}[The core idea of the whole plan]
Use a global planner for planned routes, a local collision-avoidance method for surprises,
and a replanner only when the local response is insufficient. Every week of the plan builds
one of these three abilities, or the tracking and prediction that feeds them.
\end{keyidea}

\paragraph{Study load.}
Plan for approximately 6--8 hours per week. The plan prioritizes coding over passive
reading, and so does this appendix: a good split is at most two hours of reading and four
to six hours at the keyboard. Each week has a \emph{coding exercise} and a \emph{milestone}.
The milestone is a sentence you should be able to say truthfully on the last day of the
week; if you cannot, spend the first hour of the next week closing the gap rather than
moving on.
\index{study load}

\paragraph{A weekly rhythm.}
A rhythm that works for most readers: on the first day, read the week's chapters up to the
worked example and trace that example by hand; on the next three days, write the coding
exercise, using the chapter's code file as an oracle; on the fifth day, compare your
implementation with the reference on the same instance, write the milestone sentence into
a lab notebook, and note what you would do differently. Keep the weekend as a buffer. The
notebook matters more than it looks: the capstone of Week~12, and any paper you write
afterwards, will draw on the numbers, failure cases and plots you produce in Weeks~1--11.
\index{lab notebook}

\paragraph{Suggested stack.}
The plan assumes the following tools. All of them are free, and the book's own code uses
only the first two.
\begin{itemize}
  \item \textbf{Python 3.10+ and NumPy.} Every reference implementation in this book is
    plain Python with NumPy (SciPy only for the QP and MILP solvers of
    \cref{ch:ch21,ch:ch22}). Write your own code the same way; you will read and debug it
    faster.
  \item \textbf{NetworkX} \cite{hagberg2008networkx} for quick graph experiments and for
    checking your own graph code against an independent shortest-path implementation.
  \item \textbf{Matplotlib} for the pictures the exercises ask for: \Open and \Closed sets,
    trajectories, velocity obstacles, benchmark curves. A plot you look at every ten
    minutes is worth more than a printout you look at once.
  \item \textbf{PyBullet or gym-pybullet-drones} \cite{panerati2021learning} for a 3D
    simulator with quadrotor dynamics. You need it from Week~8 onwards (continuous 3D
    planning) and for the capstone; until then a 2D NumPy simulator is enough and much
    faster to iterate on.
  \item \textbf{Your own MAPF codebase}, if you have one. The plan was written for a reader
    who already owns a swarm or MAPF simulator; reuse its grid, instance and visualization
    code so that each week's exercise is an addition, not a rewrite.
\end{itemize}
\index{Python stack}

\begin{notebox}{How the book's code files support the exercises}
Every chapter ships a Python file \code{code/chNN\_*.py} (\code{NN} is the chapter number),
and every listing in a chapter is a verbatim excerpt of that file. Each file ends with a
self-test under \code{if \_\_name\_\_ == "\_\_main\_\_":} that runs in a few seconds and
fails loudly with an \code{assert} if the implementation is wrong. Use the files in this
order: \emph{run} the self-test to see that the reference works; \emph{write} your own
version for the week's exercise without looking at the reference; then \emph{compare} both
implementations on the same instance. The reference is your oracle, not your starting
point. When the two disagree, the chapter's worked example (whose numbers were produced by
that same file) tells you which one is wrong.
\index{code files!self-test}
\end{notebox}

\section{The twelve weeks on one timeline}
\label{sec:appA-timeline}

depth in each: \emph{learn deeply} (A, B, C), \emph{know well} (D, E) and \emph{learn enough
to integrate} (F). \Cref{fig:appA-timeline} shows how the twelve weeks are distributed over

\section{Study notes, week by week}
\label{sec:appA-notes}

The notes below add to each row of \cref{tab:appA-schedule} what a table cell cannot say:
where to put your attention, what to build first, how to know that you are done, which
mistakes cost the most time, and which chapter exercises to attempt. The \emph{load}
rating, from \difficulty{1} (light) to \difficulty{3} (heavy), estimates how much of the
6--8 hours the coding exercise will take for a reader who meets the prerequisites of
\cref{ch:ch02}; plan lighter weeks around heavier ones. When a note refers to ``the coding
exercise of'' a chapter, it means the exercise marked \emph{Coding} at the end of that
chapter, which is the plan's exercise for that week.

\begin{pitfall}[Moving on with a red test]
The most expensive mistake in a self-study plan is to carry an unfinished week forward. A
space-time \astar that mishandles waiting will break the prioritized planner of Week~3,
the \cbs low level of Week~4 and the replanning layer of Week~12, and each time it will
look like a new bug. If the milestone sentence is not true on the last day of the week,
spend the first hours of the next week on it and shorten that week's exercise instead;
\cref{sec:appA-timeline} names the parts that can be compressed.
\end{pitfall}

\subsection{Week 1: Foundations -- Dijkstra and \astar}
\label{sec:appA-week01}
\index{study plan!week 01@week 1}
\noindent\textbf{Load}\ \difficulty{2}\qquad\textbf{Read}\ \cref{ch:ch03,ch:ch04}, with
\cref{ch:ch01,ch:ch02} for the vocabulary and the toolbox.
\paragraph{Focus.}
Two ideas carry the rest of the book: the settled-node invariant of Dijkstra (a node
popped from \Open with the smallest $\gcost$ has its final cost) and the role of the
heuristic in \astar (admissible: the first expansion of the goal is optimal; consistent:
no node needs re-expansion, so a \Closed set is safe). Give real time to the space-time
state $(v,t)$ with a wait action; it is the low-level search of every MAPF solver in
Part~III.
\paragraph{Build.}
A grid \astar with a pluggable heuristic (Manhattan, octile, Euclidean, zero); the same
search over $(v,t)$ with a wait action and a set of vertex and edge constraints; and a plot
that colors cells by their \Open/\Closed status after each expansion.
\paragraph{Done when.}
You can state the optimality theorem with its conditions and say what breaks when each is
dropped; your space-time search routes around a cell reserved at a given time by waiting or
detouring; and with the zero heuristic both searches expand the same nodes as Dijkstra.
\paragraph{Traps.}
An 8-connected grid with unit diagonal cost makes the octile and Euclidean heuristics
inadmissible (they assume a diagonal costs $\sqrt{2}$); a search over $(v,t)$ without a
time bound never terminates when the goal is unreachable; and an agent that stops
searching the instant it reaches the goal cannot honor a constraint on the goal cell at a
later time.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch04} is the week's deliverable. Add the coding exercise
of \cref{ch:ch03} and that chapter's treatment of backward Dijkstra as an exact heuristic;
you will reuse it as the low-level heuristic of \cbs in Week~4.

\subsection{Week 2: Dynamic replanning -- \lpastar and \dstarlite}
\label{sec:appA-week02}
\index{study plan!week 02@week 2}
\noindent\textbf{Load}\ \difficulty{3}\qquad\textbf{Read}\ \cref{ch:ch05}; \cref{ch:ch06}
if time permits.
\paragraph{Focus.}
Each vertex carries two values, $\gcost$ and $\rhs$, and a vertex is locally inconsistent
when they differ; everything else in \lpastar and \dstarlite (keys, UpdateVertex,
ComputeShortestPath) is machinery that repairs only the inconsistent vertices, in the right
order. \dstarlite searches backward from the goal so that a moving start needs only the key
modifier $k_m$ instead of a re-sort of the queue.
\paragraph{Build.}
Turn your Week-1 grid search into \dstarlite; run it in a loop in which the agent moves one
step at a time while obstacles appear and disappear in cells it has not reached; count
expansions and wall-clock time per repair and compare with a fresh \astar from the current
position.
\paragraph{Done when.}
After a small map change the number of expansions is a small fraction of a fresh \astar
(and about equal to it for a change that invalidates most of the path), and the path cost
after every repair equals the cost of a fresh \astar; that equality is the correctness test.
\paragraph{Traps.}
Forgetting to add to $k_m$ when the start moves, which leaves stale keys in the queue;
updating only one endpoint after an edge cost changes; comparing wall-clock time on grids
so small that \python overhead dominates (count expansions as well); and changing the map
in the middle of ComputeShortestPath.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch05}. If you finish early, the coding exercise of
\cref{ch:ch06}: an anytime search gives the replanning layer of Week~12 a usable path
within a time budget, which \dstarlite alone does not promise.

\subsection{Week 3: MAPF basics and conflict types}
\label{sec:appA-week03}
\index{study plan!week 03@week 3}
\noindent\textbf{Load}\ \difficulty{2}\qquad\textbf{Read}\ \cref{ch:ch07,ch:ch08}.
\paragraph{Focus.}
The formal problem of \cref{ch:ch07}: agents, time steps, actions including wait, the
conflict types (vertex, edge or swap, following, cycle) and the two objectives (sum of
costs, makespan). Decide which conflicts your project forbids and why; a swap conflict is
invisible if you compare positions only. Then \cref{ch:ch08}: prioritized planning as a
sequence of space-time \astar searches against a reservation table, fast but incomplete and
suboptimal in general, and you should be able to draw an instance that shows it.
\paragraph{Build.}
A conflict checker that takes a set of time-indexed paths and lists every conflict with its
type and time; prioritized planning for 2--5 agents; and three deliberate conflict
instances (head-on in a corridor, a crossing, an agent parked on another agent's route).
\paragraph{Done when.}
The checker finds every conflict you planted and none you did not; the planner solves the
well-formed instances; and you have an instance that prioritized planning fails for one
priority order and solves for another.
\paragraph{Traps.}
Off-by-one in time (the position at time~0 is the start; a swap compares $(u,v)$ at $t$
with $(v,u)$ at $t$); paths of different length, where the agent that has arrived stays at
its goal and must be reserved there for all later times; and a reservation table that
stores vertices but not edges.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch07} and the coding exercise of \cref{ch:ch08}. Keep the
checker: it becomes the conflict detector of your \cbs high level next week and the
``re-check inter-agent conflicts'' step of the capstone.

\subsection{Week 4: Conflict-Based Search}
\label{sec:appA-week04}
\index{study plan!week 04@week 4}
\noindent\textbf{Load}\ \difficulty{3}\qquad\textbf{Read}\ \cref{ch:ch09}.
\paragraph{Focus.}
The constraint tree. A node holds a set of constraints, one path per agent and the sum of
costs; the high level expands the cheapest node, finds its first conflict and creates two
children, each forbidding the conflict for one of the two agents; the low level replans
only the constrained agent with the space-time \astar of Week~1. Understand why optimality
follows: every conflict-free solution satisfies the constraint of at least one child, so
the split loses nothing.
\paragraph{Build.}
\cbs from scratch on a grid: vertex constraints (agent, vertex, time) and edge constraints
(agent, edge, time), a low-level search that respects them, and the high-level search.
Test with 2, 4 and 8 agents on an open grid and on the corridor instances of Week~3.
\paragraph{Done when.}
Your plans pass the Week-3 checker; the sum of costs equals that of the reference
implementation of \cref{ch:ch09} on every test instance; and you can draw the constraint
tree of a two-agent instance by hand and match it against your program's log.
\paragraph{Traps.}
An edge constraint has a direction and a time; a low-level search that returns as soon as
it pops the goal ignores constraints on the goal cell at later times (keep searching until
the time of the last such constraint); ordering the high-level queue by makespan while
reporting sum of costs; and missing conflicts after the shorter path has ended, because
its agent is still there.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch09}. Read the chapter's discussion of cardinal conflicts
and bypass, but do not implement them yet; they matter when eight agents become twenty.

\subsection{Week 5: \ecbs and practical MAPF}
\label{sec:appA-week05}
\index{study plan!week 05@week 5}
\noindent\textbf{Load}\ \difficulty{2}\qquad\textbf{Read}\ \cref{ch:ch10}; \cref{ch:ch11}
for contrast.
\paragraph{Focus.}
Bounded suboptimality. A focal search may expand any node with $\fcost \le w \cdot
\fcost_{\min}$ and picks among them the one with the fewest conflicts; \ecbs applies this
at both levels and guarantees a solution within a factor $w$ of optimal. Understand where
the lower bound comes from (the smallest $\fcost$ in each agent's low-level \Open, summed
over agents) and why the bound on the high level is stated against that lower bound.
\paragraph{Build.}
Turn your \cbs into \ecbs, or reproduce an open implementation as the plan allows, and
benchmark both on the same instances for $w \in \set{1.0, 1.1, 1.5, 2.0}$: success rate
within a time limit, runtime, high-level nodes and sum of costs, over several random seeds.
\paragraph{Done when.}
A plot of solution cost against runtime as $w$ varies, with $w=1$ reproducing \cbs exactly,
and a paragraph that states, with numbers, what suboptimality buys on your instances.
\paragraph{Traps.}
Using the current node's $\fcost$ instead of the minimum over \Open as the focal bound;
taking the returned path cost instead of the low-level $\fcost_{\min}$ as the lower bound;
forgetting to grow the focal list when $\fcost_{\min}$ rises; and drawing conclusions from
one instance.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch10}. Read \cref{ch:ch11} to know how \mstar and
Push-and-Swap differ from \cbs; the plan asks for awareness, not for an implementation.

\subsection{Week 6: Velocity Obstacles, RVO and \orca}
\label{sec:appA-week06}
\index{study plan!week 06@week 6}
\noindent\textbf{Load}\ \difficulty{3}\qquad\textbf{Read}\ \cref{ch:ch12,ch:ch13}.
\paragraph{Focus.}
Everything is relative: the relative position, the relative velocity and the Minkowski disc
whose radius is the sum of the two radii. The velocity obstacle (VO) is the set of relative
velocities that reach that disc within the horizon $\ttc$; the reciprocal velocity obstacle
(RVO) shares the avoidance between two cooperating agents; \orca turns the shared avoidance
into one half-plane per neighbor, so that choosing the new velocity is a small linear
program.
\paragraph{Build.}
A 2D simulation in which agents cross: two agents head-on first, then eight agents on a
circle exchanging places. Run three modes, no avoidance, VO and \orca, and record
collisions, minimum separation and time to goal for each.
\paragraph{Done when.}
No avoidance collides; VO avoids but oscillates or takes wide detours; \orca is smooth and
collision-free at the same speeds; and you can draw, for one pair, the collision cone and
the \orca half-plane and mark the chosen velocity.
\paragraph{Traps.}
The orientation of the half-plane (it must exclude the velocity obstacle, so the direction
of the smallest change $\vect{u}$ depends on which boundary of the cone is nearest); the
truncated cone for finite $\ttc$ is a disc plus two tangent legs, not a triangle; when the
linear program is infeasible in a dense crowd, choose the velocity that violates the
constraints least rather than stopping; and perfectly symmetric instances deadlock unless
you break the symmetry.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch12} and the coding exercise of \cref{ch:ch13}. Keep the
simulator; Week~7 and the capstone reuse it.

\subsection{Week 7: DWA and Artificial Potential Fields}
\label{sec:appA-week07}
\index{study plan!week 07@week 7}
\noindent\textbf{Load}\ \difficulty{2}\qquad\textbf{Read}\ \cref{ch:ch14,ch:ch15}.
\paragraph{Focus.}
DWA searches the velocity space: the dynamic window is the set of velocities reachable
within one control interval under the acceleration limits, admissible velocities are those
from which the robot can still stop before the nearest obstacle, and a weighted sum of
heading, clearance and velocity terms picks the command. Artificial potential fields (APF)
are the opposite extreme: no search, only a force field, attractive to the goal and
repulsive from obstacles, which is why APF is fast and why it gets stuck in local minima and
oscillates in narrow passages.
\paragraph{Build.}
Implement one of the two (DWA if your drones have real acceleration limits, APF if you want
a two-hour baseline) in the continuous simulator of Week~6, then design failure cases: a
U-shaped obstacle (an APF local minimum), a narrow passage (oscillation), and a dead end
that a short DWA horizon cannot see.
\paragraph{Done when.}
You have a picture of each failure case with an explanation of why the method fails there,
and a tuning table showing how the DWA weights (or the APF gains) change the behavior.
\paragraph{Traps.}
DWA objective terms with different units summed without normalization, so that one term
dominates; skipping the admissibility (braking) check, which collides at speed; repulsive
forces that grow without bound near obstacles (clamp them); and comparing the two methods
at different control rates.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch14} or of \cref{ch:ch15}, plus the conceptual exercises
of the other chapter. Only one of the two enters the capstone: DWA is the plan's alternative
to \orca in the local safety layer.

\subsection{Week 8: \rrt, \rrtstar and continuous 3D planning}
\label{sec:appA-week08}
\index{study plan!week 08@week 8}
\noindent\textbf{Load}\ \difficulty{2}\qquad\textbf{Read}\ \cref{ch:ch16,ch:ch17}.
\paragraph{Focus.}
The four primitives (sample, nearest, steer, collision-free) and the goal bias make \rrt;
adding the near set, parent choice and rewiring with a shrinking connection radius makes
\rrtstar asymptotically optimal; informed sampling restricts samples to the ellipsoid that
can still improve the solution. Know the difference between probabilistic completeness
(\rrt) and asymptotic optimality (\rrtstar), and what neither promises about finite time.
\paragraph{Build.}
\rrtstar, your own or from a library as the plan allows, in a 3D field of box or sphere
obstacles; compare with grid \astar on the same field discretized at two or three
resolutions: path length, computation time and memory.
\paragraph{Done when.}
A convergence plot of the \rrtstar path cost against iterations, a table that compares
\astar at each resolution with \rrtstar at each sample budget, and a one-paragraph rule for
when you would choose each.
\paragraph{Traps.}
Collision-checking the new vertex but not the segment to it; a nearest-neighbor search that
turns quadratic (use a KD-tree above a few thousand nodes); a rewire that changes a parent
without updating the costs of the descendants; and comparing raw \rrtstar paths with grid
paths without smoothing either.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch16} and the coding exercise of \cref{ch:ch17}. The 3D
field you build here is the map of the capstone.

\subsection{Week 9: Tracking unknown moving obstacles}
\label{sec:appA-week09}
\index{study plan!week 09@week 9}
\noindent\textbf{Load}\ \difficulty{2}\qquad\textbf{Read}\ \cref{ch:ch18,ch:ch19}.
\paragraph{Focus.}
The Kalman filter as two steps: predict with the motion model (the state moves, the
covariance grows) and update with the measurement (the gain weighs model against
measurement). The constant-velocity model with white-noise-acceleration process noise is
the workhorse; gating rejects outliers; a missing measurement means predict without update.
\Cref{ch:ch19} adds the extended and unscented Kalman filters (EKF, UKF) and the particle
filter for targets that turn; know when each is needed.
\paragraph{Build.}
Simulate an external drone on a curved path, observed with noisy position (and optionally
velocity) measurements at 10--20~Hz with random dropouts; track it with a Kalman filter;
tune $\mat{Q}$ and $\mat{R}$; report the error of the estimated position and velocity
against the truth next to the error of the raw measurements.
\paragraph{Done when.}
The filtered estimate is more accurate than the raw measurements, the velocity estimate is
smooth enough to extrapolate one or two seconds ahead, and the simulator of Week~6 consumes
the estimate and its covariance instead of the raw observation.
\paragraph{Traps.}
$\mat{R}$ below the real measurement noise (the filter trusts noise) or $\mat{Q}$ too
small (the filter lags on turns and its covariance becomes overconfident); a wrong $\dt$ in
the transition matrix; treating the covariance as truth when the model is violated (check
the normalized innovations); and hand-tuning on a single trajectory.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch18}; the coding exercise of \cref{ch:ch19} if your
intruder turns sharply.

\subsection{Week 10: Trajectory prediction}
\label{sec:appA-week10}
\index{study plan!week 10@week 10}
\noindent\textbf{Load}\ \difficulty{3}\qquad\textbf{Read}\ \cref{ch:ch20}.
\paragraph{Focus.}
Average and final displacement error (ADE, FDE) as the yardsticks; the constant-velocity and
Kalman baselines; the LSTM as a sequence model that reads past positions and writes future
ones; the prediction horizon and its uncertainty; and the evaluation protocol.
\paragraph{Build.}
A dataset of trajectories generated by the Week-6 simulator (agents that avoid one another
are not constant-velocity, which is what makes learning worthwhile), split by trajectory
and not by time step; a constant-velocity and a Kalman baseline; an LSTM (a deep-learning
framework is fine; the book's own code stays in NumPy); and ADE/FDE at horizons of 1, 2 and
3~seconds.
\paragraph{Done when.}
A table of ADE/FDE per horizon and per method over several training seeds, and an honest
conclusion. ``The LSTM did not beat constant velocity on this data'' is a legitimate result
and a common one at short horizons.
\paragraph{Traps.}
Leakage (the same trajectory in training and test sets); predicting absolute coordinates
instead of displacements in the agent's own frame; a weak baseline that uses the last two
noisy points instead of a smoothed velocity; comparing methods at different horizons; and
an LSTM tuned on the test set.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch20}. Save the trained model and the baselines; the
``prediction quality'' axis of the capstone uses all of them.

\subsection{Week 11: MPC and formation/communication constraints}
\label{sec:appA-week11}
\index{study plan!week 11@week 11}
\noindent\textbf{Load}\ \difficulty{3}\qquad\textbf{Read}\ \cref{ch:ch21,ch:ch23};
\cref{ch:ch22} as background.
\paragraph{Focus.}
Receding horizon: solve a short optimal control problem, apply the first input, repeat.
With the double-integrator model and a quadratic cost the problem is a quadratic program;
box constraints on velocity and acceleration are linear; separation constraints are not
convex and are linearized around the previous solution; soft constraints with slack
variables keep the program feasible. From \cref{ch:ch23}, the displacement-based formation
and its formation error. Mixed-integer linear programming (MILP, \cref{ch:ch22}) is the
exact alternative; read it to know the cost of exactness.
\paragraph{Build.}
A model predictive controller (MPC), or the simplified constrained controller the plan
allows, that follows a nominal path while keeping the formation error bounded or every
pairwise distance below the communication radius; log the constraint violations and the
slack.
\paragraph{Done when.}
With hard constraints the violation count is zero; with soft constraints the slack is
logged and small; the formation error over time is plotted; and switching the constraint
off shows a visible difference.
\paragraph{Traps.}
A horizon too long for the solver's time budget, or too short to see a conflict coming;
hard constraints that become infeasible when an intruder comes close (use slack);
linearizing a nonconvex constraint around a stale trajectory; and a model $\dt$ that
differs from the control interval.
\paragraph{Exercises.}
The coding exercise of \cref{ch:ch21} and the coding exercise of \cref{ch:ch23}; the
coding exercise of \cref{ch:ch22} is optional.

\subsection{The decision logic}
\label{sec:appA-logic}
The plan suggests the following five steps for every controlled drone, at every control
cycle. \Cref{ch:ch24} turns them into a state machine with explicit triggers (a time to
collision below a threshold, a reconnection cost above a bound, a violated constraint) and
explains what happens to the optimality of the \cbs plan once a drone leaves it.
\begin{enumerate}
  \item Follow the nominal \cbs/\ecbs path while no predicted conflict is inside the safety
    horizon.
  \item If an unknown moving object creates a near-term risk, invoke \orca/DWA to produce a
    local avoidance action.
  \item After the conflict clears, attempt to reconnect to the nominal path at a safe future
    waypoint.
  \item If reconnection is impossible, too costly, or violates formation/communication
    constraints, run \dstarlite/\astar from the current state.
  \item Re-check inter-agent conflicts after any significant replan.
\end{enumerate}
\index{decision logic!capstone}

\begin{notebox}{Keep the layers separable}
Implement each layer as a module with one entry point: the global planner takes an instance
and returns time-indexed paths; the predictor takes observations and returns a predicted
trajectory with covariance; the local layer takes the current states and predictions and
returns a velocity; the replanner takes a start state and returns a path. Then the
``avoidance strategy'' axis of the experiments is a switch, not a rewrite: local-only
disables layer~4, replan-only disables layer~3, and the hybrid uses both.
\end{notebox}
